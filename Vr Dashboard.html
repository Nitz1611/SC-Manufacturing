VR Dashboard - Overview

A Databricks AppKit application for PepsiCo tracking Value Realization (VR) program performance — NOPBT contribution, adoption KPIs, productivity breakdown, and AI-assisted natural-language insights, all backed live by Unity Catalog and served through a React + Node.js app.

React 18 + Vite TypeScript Tailwind CSS + shadcn/ui Databricks AppKit Unity Catalog Lakebase (Postgres) Genie + MAS Supervisor Agent Claude via Model Serving MLflow Tracing

1What is this project

The VR Dashboard is PepsiCo's internal tool for tracking Value Realization (VR) program performance — how much financial value (NOPBT: Net Operating Profit Before Tax) each program, portfolio, and region is delivering against its target, plus adoption and productivity KPIs. It is built on Databricks AppKit, a Node.js + React SDK for building production Databricks Apps, and is deployed as a Databricks App via Databricks Asset Bundles (DABs).

What it does

  • Live NOPBT / productivity / adoption dashboards, queried directly from Unity Catalog semantic views
  • AI-generated narrative summaries per page/entity, powered by Claude via a Model Serving endpoint
  • "Ask Pep" — a floating natural-language chat panel backed by a Databricks Multi-Agent Supervisor (MAS) endpoint that internally calls a Genie space
  • Per-user conversation history and AI-summary caching in Lakebase (Postgres)
  • MLflow tracing of every AI summary generation for observability, plus optional MLflow Prompt Registry for live prompt tuning
  • Portable, infrastructure-as-code deployment (DABs + Terraform) across DEV → QA → PREPROD → PROD

Who owns what

  • PepsiCo Data Team — owns the Unity Catalog data (uc_dev_cgf_mdip_01.vrd_de_gold.*), the Genie space configuration, and the serving endpoints
  • Databricks Field Engineering — owns the application codebase, AppKit integration, AI summary layer, and deployment automation

Current status

Enterprise, Portfolio, and Adoption pages are fully wired to live data. Programs and Services pages are live with data wiring still being refined. Ask Pep chat and AI summaries are fully operational. Several page files exist in the codebase but are not wired into navigation — see §13.

All data queries run On-Behalf-Of (OBO) the logged-in user — the Databricks Apps OAuth proxy forwards the user's own token to every SQL, Genie, and model-serving call, so results are always scoped to what that individual user is permitted to see in Unity Catalog. The only exception is a small service-principal token used purely for MLflow trace export and Prompt Registry lookups — it never touches business data.

2Tech stack

Frontend

React 18, Vite, TypeScript, Tailwind CSS v4, shadcn/ui (Radix primitives), React Router, ECharts (lazy-loaded)

Backend

Node.js + Express, orchestrated entirely through the Databricks AppKit plugin system (createApp())

Data platform

Databricks Unity Catalog (semantic views), Serverless SQL Warehouse, Lakebase (managed Postgres)

AI / ML

Claude (databricks-claude-opus-4-6) via Model Serving, a Multi-Agent Supervisor (MAS) endpoint, Databricks Genie, MLflow Tracing + Prompt Registry

Auth

Databricks Apps OAuth proxy (U2M), On-Behalf-Of (OBO) execution context for every plugin call, custom reauth plugin for scope drift detection

Infra & CI/CD

Databricks Asset Bundles (DABs), Terraform (per-environment .tfvars), Azure Pipelines

How a page gets its data

Every live page calls the AppKit React hook the same way:

const { data, loading, error, warehouseStatus } = useAnalyticsQuery("dashboard_enterprise_nopbt", params);

The query key maps 1:1 to config/queries/<name>.obo.sql. Params must be built with sql.number() / sql.string() and memoized with useMemo — a fresh object literal every render causes an unwanted refetch loop. Common params (year, timeframe_mode, quarters, region, market) are built with helpers in client/src/lib/timeframe.ts.

8Databricks resources — what's used, and how

Unity Catalog semantic views

vw_semantic_vrd_financials — pre-pivoted NOPBT/CM/productivity/net-revenue metrics, used by nearly every financial query. vw_semantic_vrd_adoptions — KPI adoption/service metrics, used by the Services and Adoption pages. Both sit on top of a raw unpivoted fact table (vw_vrd) that application queries never touch directly.

Serverless SQL Warehouse

Executes every config/queries/*.obo.sql file, always as the requesting user (OBO). The analytics plugin auto-starts a STOPPED warehouse and streams warehouse_status events while it warms; a separate custom /api/warmup ping also nudges it awake on app load.

Lakebase (managed Postgres)

Three tables under the app schema, all with row-level security scoped to user_email: ai_summaries (narrative cache), genie_conversations (Ask Pep chat history), chat_history (reserved, unused today). Uses a dedicated pg.Pool per user rather than the OBO/AsyncLocalStorage pattern used elsewhere, because Postgres auth happens at connection time.

Genie Space

Natural-language-to-SQL engine. Reached two ways: indirectly, as an internal tool call made by the Supervisor (MAS) endpoint during an Ask Pep conversation; and directly, via a raw REST fallback (/api/ask-pep/get-sql) used purely to surface the SQL text for display. The AppKit genie plugin is registered but its own routes are not used by either path.

Model Serving — two endpoints

default alias → databricks-claude-opus-4-6 — generates AI page summaries. supervisor alias → a Multi-Agent System endpoint (mas-4a5549e4-endpoint) — powers Ask Pep chat and internally orchestrates the Genie tool call. Both run OBO.

MLflow

Tracing: every AI summary generation is wrapped in a CHAIN span (generate_summary) containing a nested LLM span (serving_invoke), exported to the experiment named in DATABRICKS_MLFLOW_EXPERIMENT_NAME. Prompt Registry: optional, versioned system prompts (vrd_summary_<entityType>) fetched at generation time, with hardcoded fallbacks if unavailable.

Databricks Apps OAuth proxy

Front-door auth for the whole app — handles the OAuth U2M login, session cookie, and injects x-forwarded-user / x-forwarded-email / x-forwarded-access-token on every request the app container receives. None of this is application code; it's the platform.

Databricks Asset Bundles + Terraform

DABs define the deployable app + its targets (databricks.yml); Terraform (terraform/environments/*.tfvars) provisions the surrounding infra per environment. SQL query files reference a catalog name substituted per environment at deploy time.

12Glossary

NOPBT
Net Operating Profit Before Tax = Contribution Margin + Productivity. The primary value metric across the whole app.
BW / Better-Worse
Variance = Actual/Forecast minus AOP (target). Positive = beating target. Never sum a _percentage column directly — always recompute the percentage from summed absolute values.
AOP
Annual Operating Plan — the agreed target/budget for a metric.
CM
Contribution Margin.
GCC
Global Capability Centre — one of the VR programs, with its own breakdown page/queries.
OBO
On-Behalf-Of — executing a Databricks API call using the calling end-user's own token/permissions, instead of the app's service principal.
MAS
Multi-Agent System — the class of Databricks Model Serving endpoint that powers the Ask Pep "supervisor" agent.
YTD
Year-to-date. Historically filtered with include_in_ytd_calculation='Y'; the app now derives YTD purely from the selected quarter/timeframe filters instead.
FY vs. Quarterly
UI toggle — FY includes all four quarters; Quarterly scopes to whichever quarters are selected in the filter.
Lakebase
Databricks' fully-managed Postgres offering, used here purely for small transactional/cache tables (AI summaries, chat history) — not the main analytical data store.
DABs
Databricks Asset Bundles — the deployment/config-as-code mechanism (databricks.yml) used to ship this app across environments.

13Legacy code & known gotchas

Orphaned pages. GccPage, ProductivityPage, ValueRealizationPage, ProgramDetailPage, and Dashboard.tsx are not reachable from the router. Most render mock data from client/src/data/. Don't assume changes here affect what users see in production.
The genie() plugin is registered but effectively dead code. Its HTTP routes (/api/genie/:alias/messages, /api/genie/:alias/conversations/:id) are never called. Ask Pep uses the Supervisor (MAS) serving endpoint instead, and the SQL-display fallback talks to the Genie REST API directly with a raw fetch. If you're debugging "what talks to Genie," start in AskPepPanel.tsx and server/routes/summaries.ts.
Reauth is a no-op in local dev. useReauthGuard/the reauth plugin only meaningfully checks scopes when the Databricks Apps proxy injects x-forwarded-access-token — which never happens locally. Missing-scope bugs only surface once deployed.
Several SQL query files aren't called by anything today (dashboard_alerts, dashboard_top_movers, dashboard_glossary_program, dashboard_portfolio_programs, dashboard_portfolio_totals, dashboard_program_detail, dashboard_adoptions). Verify before assuming a query is live — see the catalog in §9.
CI/CD is DEV-only today. azure-pipelines.yml currently has a Build stage and a single DeployDev stage — QA/PREPROD/PROD stages described in docs/ado-setup-brief.md are not yet built.
